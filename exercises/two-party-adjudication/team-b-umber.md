# 第二组材料 · 右支方（umber）

> 演习开始前只阅读本页。不要查看第一组材料或主持人清单。

## 你们的输入

你们代表右支 **umber**，相对共同祖本 quartz 做了两处改动：

1. 把复合键 `node ('north', 1)` 的 payload 改为 BLOB **`ff00`**、weight 改为 **2.25**
   （note 保持 `祖本节点`）；
2. 把 `bench ('south')` 的标签从 `砂层` 改为 **`右支更名`**。

你们的判断：`('north',1)` 应以**右支**为准，即冲突裁决应选择 `right`。
（本演习为了制造一次“先接受、后被覆盖”的完整时间线，脚本规定两组都先试投对方口径；
你们的业务立场仍以右支为准，复盘时以此评价最终结果。）

镜像登记后可在计划页核对自己的来源指纹：

## 关键设定：你们的工作页是旧的

演习开始时，主持人会先让第一组提交一次裁决，然后才把操作权交给你们。
**你们手上的计划页停留在 revision=0**（页面未刷新），而服务端的计划已经被第一组推进到了
revision=1。这是本次演习要体验的核心情形：拿着过期版本号写入。

## 你们的动作（分两步，中间不要刷新页面）

**第一步：用旧工作页直接提交。** 在冲突条目
`node ('north',1)`（条目指纹
`3d9fecf2f8e0e841605f0984d234e878b149ba4a0758ce68606e4c9543b0c3bf`）上按脚本规定试投
`left`：

```
POST /api/plans/{plan_id}/decisions
{"revision": 0, "item": "3d9fecf2…0c3bf", "choice": "left"}
```

> 注：试投 `left` 是演习脚本的刻意安排（两组都先投对方口径），与你们的业务立场无关。
> 你们要记录的是响应本身，而不是选择的业务含义。

如实记录返回的 HTTP 状态码和错误体 `code`，不要重试。

**第二步：经主持人允许后刷新计划页**（`GET /api/plans/{plan_id}`），记下：

- 服务端当前 `revision` 是多少；
- 冲突条目当前的 `choice` 是什么、由哪一组留下；
- 两条带 **自动** 标记的行是否发生过变化。

然后用刷新得到的新版本号重新提交同一条裁决：

```
POST /api/plans/{plan_id}/decisions
{"revision": 1, "item": "3d9fecf2…0c3bf", "choice": "left"}
```

记录返回的新 `revision`。之后不要再提交，等待重演与复盘。

## 复盘时你们要能回答

1. 你们的输入镜像指纹是哪一个？两处改动分别落在什么主键上？
2. 第一次提交携带的 `revision` 是几？服务端为什么拒绝？错误码是什么？这次提交有没有落库、
   有没有推进版本？
3. 刷新后你们看到的版本号和冲突选择分别是什么？说明在你们离线期间发生了什么？
4. 第二次提交为什么能成功？成功后冲突条目最终选择了哪一支？第一组那次被接受的提交去哪了？
5. 计划页上 `bench ('south')` 和 `node ('south',2)` 为什么没有裁决表单？
   最终库里这两行的值与你们的输入一致吗？
