# Pagefold 适用性评审样本

四组可运行的三方 SQLite 镜像，用于评审本工作区在**小冲突**、**密集自动更新**、
**大量相同行**三种情形下是否适用；另设一组**空转裁决**，刻意让有效成果少于计划条目。
所有样本确定性生成（无随机因素），操作观察来自真实 HTTP 全流程。

## 四组设计

| 组 | 情形 | 祖本规模 | 分支差异 | 计划条目 | 待裁决 | 重演变更 |
|---|---|---|---|--:|--:|--:|
| `a-small-conflict` | 小冲突 | 18 行 | 1 处双边冲突 ＋ 4 处单边变化 | 5 | 1 | 5 |
| `b-dense-auto` | 密集自动更新 | 4,000 行 | 左右支共 1,500 处互不重叠的改动 | 1,500 | 0 | 1,500 |
| `c-bulk-identical` | 大量相同行 | 16,000 行 | 仅 7 处差异（99.96% 行三方相同） | 7 | 1 | 7 |
| `d-noop-decisions` | 空转裁决 | 48 行 | 6 项冲突中 4 项刻意裁决为祖本 | 10 | 6 | **6** |

四组共用同一模式：`entry(id INTEGER PRIMARY KEY, …) STRICT` ＋
`tag(entry_id, label) STRICT, WITHOUT ROWID`（外键 → entry）＋ 索引 `tag_label`；
每组三份镜像的建表与索引记录逐字节一致。

## 复现

```sh
python3 -m review.make_samples           # 生成 review/images/ 与 MANIFEST.md、manifest.json
python3 -m review.make_samples --check   # 校验已生成镜像可逐字节复现
python3 -m review.run_review             # 真实 HTTP 操作，生成 OBSERVATIONS.md、observations.json
```

镜像文件不入库（`.gitignore` 忽略 `*.sqlite`）；重跑第一条命令即可得到与
`MANIFEST.md` 中 SHA-256 完全相同的 12 份镜像。

## 文件构成

| 文件 | 说明 |
|---|---|
| `review/groups.py` | 四组的共享定义：模式、数据、变更、裁决策略、预期结果 |
| `review/make_samples.py` | 生成镜像；用**独立于 pagefold** 的 SQL 逐键对比产出差异表 |
| `review/run_review.py` | 走真实 HTTP 入口完成全流程并校验，记录耗时与结果 |
| `review/MANIFEST.md` | 文件清单（字节、行数、SHA-256）＋ 每组来源说明与差异表 |
| `review/OBSERVATIONS.md` | 真实操作观察记录（会议版）；原始数据在 `observations.json` |
| `review/images/<组>/{base,left,right}.sqlite` | 生成的样本镜像（不入库） |

## 为什么输入体积与计划条目数不成比例

评审时容易直觉地认为"输入越大、计划条目越多"。实测四组的比例（条目/千行输入）
分别为 **90.91、120.97、0.15、69.44**，相差三个数量级。这是机制决定的，而非异常：

1. **计划条目按"键"计，不按字节计。** `merge.calculate` 对三份快照逐键对比，
   **三方相同的键直接跳过**（`pagefold/merge.py:16-17`）。所以 C 组 48,000 行输入
   只有 7 条计划——15,995 行相同行被正确忽略，**大量相同键 ≠ 大量变更**。
2. **输入字节与条目数无线性关系。** 镜像体积还包含索引页、空闲页与模式记录；
   C 组单份 417 KB 与 A 组单份 16 KB 相差 25 倍，条目数却是 7 对 5。
3. **自动项也是条目。** 单边变化的每一行各占一条（B 组 1,500 条全部自动采纳、
   零冲突），条目数随变更行数线性增长，与是否需要人工裁决无关。
4. **条目 ≠ 有效变更。** `replay.amendments` 只统计"所选行 ≠ 祖本行"的条目
   （`pagefold/replay.py:18-19`）。D 组 4 项冲突裁决为祖本后，10 条计划只产生
   6 行实际变更——计划条目数不夸大有效成果。
5. **耗时随输入行数走，不随条目数走。** 建计划与重演都要全量扫描并校验整个快照：
   C 组（16,000 行/份）计划 247 ms、重演 148 ms；A 组（18 行/份）均约 6 ms。

## 初步结论（供会议讨论）

- **小冲突：适用。** 未决拦截（409 unresolved）、过期版本拒绝（409 stale_revision）、
  同值裁决幂等、封存后归档且凭证稳定，全流程行为正确。
- **密集自动更新：适用，留意计划体积。** 1,500 个自动项零冲突通过，重演 68 ms；
  计划响应 641 KB / 1,500 条，条目与计划体积随变更行数线性增长，万级变更前无需特殊处理。
- **大量相同行：适用。** 相同行不产生条目，48,000 行输入仅 7 条计划、计划响应 3 KB；
  成本体现在全量扫描（16,000 行/份时计划 247 ms），接近 20,000 行上限仍在秒级以内。
- **空转裁决：行为正确。** 重演变更数（6）小于计划条目数（10）被如实反映，
  祖本裁决不写入候选；凭证 decision_digest 绑定全部裁决，可追溯。
- 四组的 pagefold 计划条目与本目录独立差异表**逐项一致**（共 97 项校验全部通过），
  差异表与来源说明见 `MANIFEST.md`，操作细节见 `OBSERVATIONS.md`。
